# Ускорение запуска приложения — дизайн

Дата: 2026-10-29

## Проблема

При запуске пользователь 3–4 секунды видит крутящийся индикатор загрузки (iPhone; на Android около 2,3 с до экрана и 3 с до заполненных карточек).

Замер `[PERF]` на Samsung A27 (участник, без PIN):

| Шаг | Время | Последовательно |
|---|---|---|
| `getProfile` (первый запрос) | 1213 мс | — |
| `getGroupsByAdminIds` (проверка «не админ ли») | 356 мс | да |
| `getGroupById` | 338 мс | да |
| участники + показатели + периоды | ~400 мс | да |
| отчёты → `getMetricValues` на каждый | ~660 мс | да |

Причины:
- база Supabase в Сеуле (`ap-northeast-2`), каждый запрос ~300 мс;
- первый запрос дороже (новое соединение, при долгом простое — обновление токена);
- 4–5 последовательных шагов, часть из них лишние.

## Цель

- Повторный запуск: главный экран сразу из кэша, без индикатора загрузки; свежие данные подменяют кэш за 1–2 с.
- Первый запуск (кэша нет): быстрее примерно на 0,6 с.

## Часть 1. Меньше последовательных запросов

1. **AuthGate:** `getProfile(user.id)` и `getGroupsByAdminIds([user.id])` выполняются параллельно (оба зависят только от `user.id`). Результат используется и для решения о PIN, и для маршрутизации — без повторных запросов.
2. **Отчёты:** запросы чтения отчётов (`getReport`, `getReportByPeriod`, `getGroupReports`, `getGroupReportsByPeriod`, `getUserRecentReports`) получают значения показателей встроенно: `select('*, report_metric_values(metric_id, value)')` (FK `report_metric_values.report_id → ibadat_reports.id` есть). Если встроенных данных нет (например, ответ на upsert), остаётся текущий путь через `getMetricValues`. Ответы на upsert/insert/update не меняются — значения для них читаются после `replaceMetricValues`.

## Часть 2. Кэш стартовых данных

### Хранилище

`lib/cache/startup_cache.dart` — `StartupCache` поверх `SharedPreferences`:
- ключ `startup_cache_v1:<userId>:<name>`; значение — JSON;
- `read(userId, name)` → `Object?` (null при отсутствии/ошибке разбора);
- `write(userId, name, value)`; ошибки игнорируются;
- `clear()` удаляет все ключи с префиксом `startup_cache_v1:`.

### Сериализация моделей

У `IbadatProfile`, `IbadatGroup`, `GroupMetric`, `IbadatPeriod`, `IbadatReport` появляется `toCacheJson()` — точная обратная к `fromJson` (`Model.fromJson(m.toCacheJson())` даёт те же поля). Существующие `toJson` (используются для записи в базу) не меняются.

### Что кэшируется

| Имя | Содержимое | Кто пишет / читает |
|---|---|---|
| `auth` | `{profile, owns_group}` (профиль как в базе, флаг «админ какой-то группы») | AuthGate |
| `group` | текущая группа | MainScaffold |
| `home` | снимок главного экрана (участник или админ) | HomeScreen |

Снимок главного экрана (`lib/cache/home_snapshot.dart`):
- участник: `group_id`, участники, показатели, периоды, отчёты текущего периода, отчёты тренда;
- админ: секции групп (группа, участники, показатели, периоды, отчёты текущего периода, тренд), личные показатели, личные периоды, личный отчёт.

Снимок хранит и индекс выбранного периода (и месяц/год для режима без периодов), чтобы отчёты в снимке соответствовали показанному периоду.

### Поведение

**AuthGate.** Есть сессия:
- есть кэш `auth` → сразу решение о PIN и маршрут по кэшу (без сети), затем в фоне `_loadProfile` (параллельные запросы из части 1). Свежий результат пишет кэш и при отличии меняет маршрут. Если свежий результат требует PIN (есть PIN, пользователь больше не админ группы), а PIN в этой сессии ещё не вводился — показывается экран PIN;
- кэша нет → как сейчас, но с параллельными запросами.

**MainScaffold.** Есть кэш `group` с `id == profile.currentGroupId` → вкладки строятся сразу, свежая группа подменяет кэш.

**HomeScreen.** Есть подходящий снимок (участник: тот же `group_id`; админ: роль админа) → данные показываются сразу, индикатор загрузки не показывается, затем обычная загрузка без индикатора. После полной загрузки (включая отчёты) снимок перезаписывается. Индикатор загрузки на весь экран — только когда показать нечего.

Выбор периода при обновлении: если был выбран последний период, после обновления выбирается новый последний (на случай добавленного периода); иначе выбор сохраняется.

**Очистка.** `AuthLogoutService.clearLocalAccountState` (выход и удаление аккаунта) вызывает `StartupCache.clear()`. Кэш привязан к `userId`, поэтому другой аккаунт на том же телефоне чужой кэш не прочитает.

### Ошибки

- Повреждённый/несовместимый кэш → игнорируется (null), загрузка по сети.
- Ошибка сети при наличии кэша → остаются данные из кэша (как сейчас при ошибке в фоне).

## Вне рамок

- Кэш вкладок «Отчёт», «Платежи», «Админ».
- Перенос проекта Supabase в другой регион.
- Объединение запросов в одну функцию (RPC).

## Тестирование

- `StartupCache`: запись/чтение, разные `userId`, повреждённый JSON → null, `clear`.
- `toCacheJson` ↔ `fromJson` для 5 моделей.
- Снимок главного экрана: туда-обратно для участника и админа.
- Репозиторий отчётов: встроенные значения используются без `getMetricValues`; без них — старый путь.
- `clearLocalAccountState` очищает кэш.
- Ручной замер `[PERF]` на Android: холодный старт с кэшем и без.
